📟 A PROGRAM is not a PROCESS

🎯 核心概念：程序(Program)是被动的静态实体，而进程(Process)是主动的动态实体。

🕰️ 历史背景

计算机科学中有一个常见问题：我们该如何称呼 CPU 执行的所有活动？

时代 术语 特点
🖥️ 批处理系统 作业 (Job) 一次执行一个任务
⏳ 分时操作系统 运行用户程序 (ran user programs) 多用户共享 CPU 资源
💻 现代操作系统 进程 (Process) 单用户同时运行多程序

后来 分时操作系统(time-sharing operating systems) 出现，系统允许多用户共享 CPU 资源。 现在家用计算机普及，并发技术实现了单用户可以同时运行多个程序。 在计算机科学中，我们称这些实体为 进程(processes)，而不是程序(programs)。

🔬 什么是进程？什么是程序？

通俗定义

进程通常被定义为"正在执行的程序"，但这个定义并不完全触及进程的实质。我们可以先通过反例来理解进程不是什么。

📦 程序 (Program) — 静态实体

程序是由 指令序列 及其所需 数据 组成的静态实体，用于指导 CPU 完成特定任务。 这个定义同样适用于 可执行文件(executable file)。

程序静静地存储在磁盘上，等待用户点击执行命令，载入内存。

⚡ 进程 (Process) — 动态实体

程序被载入内存时，可执行代码所在的区域称为 代码段(text section)， 而全局变量和常量等数据则存放在 数据段(data section)。

运行程序仅靠这两部分是远远不够的，我们需要额外的内存空间来存储运行时产生的数据（如用户输入、临时结果或变量）。

🧠 进程的内存布局

区域 英文 说明 增长方向
📄 代码段 Text Section 可执行代码（指令序列） 固定
📊 数据段 Data Section 全局变量、常量等静态数据 固定
📚 栈 Stack 函数调用、局部变量、返回地址 ⬇️ 向下增长
🗃️ 堆 Heap 动态内存分配（malloc/new） ⬆️ 向上增长 
高地址
  ┌─────────────────────┐
  │       栈 (Stack)     │  ← 向下增长
  │      (局部变量)      │
  ├─────────────────────┤
  │         ↓↑          │  ← 空闲内存
  ├─────────────────────┤
  │       堆 (Heap)      │  ← 向上增长
  │      (动态分配)      │
  ├─────────────────────┤
  │     数据段 (Data)    │  ← 全局变量、常量
  ├─────────────────────┤
  │     代码段 (Text)    │  ← 可执行指令
 低地址
程序 → 进程 的转变

程序被载入内存并进入运行时后，内存布局发生了根本性改变。 从这时开始，程序转变为了进程。

💡 实例分析：文本编辑器

想象你用文本编辑器同时打开两个不同的文本文件进行编辑：

┌─────────────────────────┐    ┌─────────────────────────┐
│   🚀 进程 A (PID: 100)   │    │   🚀 进程 B (PID: 101)   │
│   📄 readme.txt          │    │   📄 notes.txt           │
│                          │    │                          │
│   代码段: 相同 ✅         │    │   代码段: 相同 ✅        │
│   数据段: 独立 ❌         │    │   数据段: 独立 ❌        │
│   堆 / 栈: 独立          │    │   堆 / 栈: 独立          │
└──────────┬──────────────┘    └──────────┬──────────────┘
           │                              │
           └────────── 同一套程序 ─────────┘
  • 操作系统会启动两个完全独立的文本编辑器实例
  • 出现两个独立窗口，分别显示不同的文件内容
  • 它们运行 同一套程序代码，但形成 两个完全独立的进程
  • 如果第一个进程处理的文件更大，它自然需要更大的内存来管理数据

📊 程序 vs 进程：对比总结

维度 🏗️ 程序 (Program) 🚀 进程 (Process)
本质 被动实体 主动实体
存储位置 磁盘 (Disk) 内存 (Memory)
生命周期 永久存在（文件） 创建 → 运行 → 终止
资源占用 仅有磁盘空间 CPU + 内存 + I/O
对应关系 一个程序可对应多个进程 每个进程对应一个程序
类比 📜 乐谱 🎵 演奏
核心结论

即使两个进程关联着相同的程序，它们仍然被视为 两个独立的执行序列。

🗺️ 进程的五状态模型

进程在其生命周期中会经历不同的状态。操作系统正是通过管理这些状态来实现多任务并发。

状态转换图

         ┌───────────┐
         │  🆕 New   │
         └─────┬─────┘
               │ admitted (允许进入)
               ▼
   ┌─────────────────────┐
   │     ✅ Ready        │◄──────┐
   │  (等待 CPU 调度)    │       │
   └──────────┬──────────┘       │
              │ dispatch (调度)  │
              ▼                  │
   ┌─────────────────────┐       │
   │    ▶️ Running       │       │
   │    (CPU 执行中)     │       │
   └──┬───────┬──────────┘       │
      │       │                  │
  I/O │       │ exit (终止)      │
      │       ▼                  │
      │  ┌───────────┐          │
      │  │ ❌ Term.  │          │
      │  └───────────┘          │
      ▼                         │
   ┌─────────────────────┐      │
   │   ⏸️ Waiting        │      │
   │ (等待 I/O 或事件)   │      │
   └──────────┬──────────┘      │
              │ I/O complete    │
              └─────────────────┘
              (被抢占时回到就绪)

状态说明

状态 英文 说明
🆕 新建 New 进程正在被创建，尚未就绪
✅ 就绪 Ready 已准备好运行，等待 CPU 调度
▶️ 运行 Running CPU 正在执行该进程的指令
⏸️ 等待 Waiting 等待 I/O 完成或某个事件发生（也称阻塞 Blocked）
❌ 终止 Terminated 进程执行完毕，正在被系统清理
状态转换规则
  • 就绪 → 运行：由调度程序(scheduler)分配 CPU
  • 运行 → 就绪：时间片耗尽或被更高优先级进程抢占(preempt)
  • 运行 → 等待：进程请求 I/O 操作或等待某事件
  • 等待 → 就绪：I/O 完成或事件到达

📋 进程控制块 (PCB)

PCB (Process Control Block) 是操作系统内核中用于管理进程的核心数据结构。

⚡ 核心要点

PCB 的作用

每创建一个进程，OS 就为其创建一个 PCB。 操作系统不直接操作进程本身，而是通过 PCB 来感知和控制进程。PCB 是 OS 管理进程的 唯一依据。

PCB 包含的关键信息

信息类别 内容
🆔 进程标识 PID (Process ID)、父进程 PID
📊 进程状态 New / Ready / Running / Waiting / Terminated
📐 程序计数器 下一条要执行的指令地址
💾 CPU 寄存器 通用寄存器、栈指针、状态字等
📏 内存管理 段表 / 页表、内存边界寄存器
📂 打开文件列表 进程当前打开的所有文件描述符
⏰ 调度信息 优先级、时间片、已使用 CPU 时间
📈 I/O 状态 分配给进程的 I/O 设备列表 
// PCB 的简化示意结构（类 Linux 风格）
struct task_struct {
    // ── 进程标识 ──
    int pid;                    // 进程 ID
    int ppid;                   // 父进程 ID

    // ── 进程状态 ──
    volatile long state;        // 进程状态 (-1 不可运行, 0 可运行, >0 停止)

    // ── CPU 上下文 ──
    uint64_t program_counter;   // 程序计数器 → 下一条指令地址
    uint64_t *registers;        // CPU 寄存器快照

    // ── 内存管理 ──
    struct mm_struct *mm;       // 内存描述符（页表、段表）

    // ── 文件系统 ──
    struct file **files;        // 打开的文件描述符表

    // ── 调度信息 ──
    int priority;               // 调度优先级
    unsigned int time_slice;    // 时间片
};

🔄 上下文切换 (Context Switch)

上下文切换 是指 CPU 从一个进程切换到另一个进程时，保存当前进程的状态并加载下一个进程状态的过程。

切换流程图

     进程 A 正在运行
          │
          ▼
  ┌──────────────────────────────┐
  │  ⏸️ 保存进程 A 的上下文       │
  │   └→ CPU 寄存器 → PCB_A       │
  │   └→ 程序计数器 → PCB_A       │
  │   └→ 页表基址 → PCB_A         │
  └──────────────┬───────────────┘
                 ▼
  ┌──────────────────────────────┐
  │  🔄 OS 执行调度程序 (Scheduler)│
  │   └→ 从就绪队列选择下一个进程  │
  └──────────────┬───────────────┘
                 ▼
  ┌──────────────────────────────┐
  │  ▶️ 恢复进程 B 的上下文       │
  │   └→ PCB_B → CPU 寄存器       │
  │   └→ PCB_B → 程序计数器       │
  │   └→ PCB_B → 切换页表         │
  └──────────────┬───────────────┘
                 ▼
     进程 B 开始运行
切换是纯开销

上下文切换本身是 纯开销（在这段时间内 CPU 没有做任何有用的计算工作），但又是多任务操作系统不可或缺的机制。OS 设计需要在 响应速度 和 切换开销 之间取得平衡。

上下文切换的开销

开销类型 说明
⏱️ 时间开销 保存 / 恢复寄存器、切换内存映射、刷新 TLB
💾 空间开销 内核栈、PCB 存储占用
🌡️ 缓存污染 L1/L2 Cache 失效，新进程需重新预热 
# 伪代码：上下文切换的核心逻辑
def context_switch(prev, next):
    # 1. 保存前一个进程的 CPU 状态
    save_registers_to_memory(prev.registers, prev.registers_ptr)
    save_program_counter(prev.program_counter)

    # 2. 更新进程状态
    prev.state = READY     # 或 WAITING
    next.state = RUNNING

    # 3. 切换内存映射（刷新 TLB）
    switch_page_table(next.page_table)

    # 4. 恢复下一个进程的 CPU 状态
    restore_registers_from_memory(next.registers, next.registers_ptr)
    restore_program_counter(next.program_counter)

    # CPU 从新位置继续执行

🧬 进程的创建

不同操作系统创建进程的方式有所不同：

Unix/Linux：fork() + exec() 模式

         ┌───────────────────────┐
         │   父进程 (PID: 100)    │
         │   正在运行...          │
         └──────────┬────────────┘
                    │ fork()
                    ▼
         ┌───────────────────────┐
         │ fork() 系统调用        │
         │                       │
         │  ├ 创建子进程的 PCB     │
         │  ├ 复制父进程的内存空间  │
         │  └ 子进程获得新 PID:101│
         └──────────┬────────────┘
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
  ┌──────────────┐   ┌──────────────┐
  │ 父进程继续执行 │   │ 子进程执行    │
  │              │   │ exec() 系统   │
  │ wait() 等待  │   │ 调用加载新    │
  │ 子进程结束    │   │ 程序替换镜像  │
  └──────────────┘   └──────────────┘

// Unix/Linux 创建进程的标准模式
pid_t pid = fork();  // 创建子进程（复制当前进程）

if (pid == 0) {
    // 子进程：加载并执行新程序
    execl("/bin/ls", "ls", "-l", NULL);
} else if (pid > 0) {
    // 父进程：等待子进程结束
    wait(NULL);
}

Windows：CreateProcess()

// Windows 一步到位
CreateProcess(
    "C:\\Windows\\System32\\notepad.exe",  // 程序路径
    "readme.txt",                           // 命令行参数
    NULL, NULL,                             // 安全属性
    FALSE,                                  // 句柄继承
    0,                                      // 创建标志
    NULL,                                   // 环境变量
    NULL,                                   // 当前目录
    &si,                                    // 启动信息
    &pi                                     // 进程信息（返回 PID 等）
);
fork() 写时复制优化

fork() 不会立即复制全部内存，而是采用 写时复制(Copy-on-Write) 技术： 父进程和子进程共享同一份物理内存，只有当某一方试图写入时，才真正复制。

这样可以大幅减少进程创建的开销。

🌐 编译型 vs 解释型语言

以上讨论的经典进程模型对 编译型语言（C、C++、Go、Rust）完全成立。C 和 Rust 编译生成的都是可执行文件 —— 也就是 程序本身。

但对于 解释型语言（Python、JavaScript、Lua）来说，情况有所不同。每次运行代码时，我们都需要先启动解释器，再通过解释器执行代码。

这里面涉及两个被动实体：

实体 本质 是"程序"吗？
🐍 Python 解释器 可执行文件 (二进制) ✅ 是
📄 你的 .py 文件 纯文本文件 ❌ 不是 
# 你以为是运行这个文件：
print("Hello OS")

# 但实际上 OS 运行的是：
python3 hello.py
# ↑       ↑
# 程序    数据
解释型语言的执行流程
  1. OS 将 Python 解释器 载入内存 → 创建进程
  2. 代码段中加载的是 解释器的二进制代码，不是你的 Python 代码
  3. 你的 Python 源代码被解释器读取到堆区，作为数据处理
  4. 解释器逐行读取并执行这份"数据"
