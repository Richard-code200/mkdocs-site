## 断言宏(Assertion Macros)

Rust 提供了一组内置宏用于验证程序的正确性,断言失败时程序会 **panic** 并打印错误信息.

### assert

断言一个布尔表达式为 `true`:

```rust
fn main() {
    let x = 5;
    assert!(x > 0);
    assert!(x % 2 != 0, "x should be odd, got {x}"); // 可附加错误信息
}
```

### assert_eq

`eq` 是 equal(相等)的缩写.断言两个值**相等**(使用 `==` 比较):

```rust
fn main() {
    let result = 2 + 2;
    assert_eq!(result, 4);
    assert_eq!(result, 5, "expected 5, got {result}"); // 可附加错误信息
}
```

### assert_ne

`ne` 是 not equal(不相等)的缩写.断言两个值**不相等**(使用 `!=` 比较):

```rust
fn main() {
    let result = 2 + 2;
    assert_ne!(result, 5);
}
```


> [!info] 三种断言宏对比
> 
> | 宏           | 含义          | 失败条件       |
> | ------------ | ------------- | -------------- |
> | `assert!(e)` | `e` 为 `true` | `e` 为 `false` |
> | `assert_eq!` | 两个值相等    | 两个值不相等   |
> | `assert_ne!` | 两个值不相等  | 两个值相等     |
> 



> [!warning] 使用前提
> `assert_eq!` 和 `assert_ne!` 要求比较的类型实现了 `PartialEq` trait.如果需要在失败信息中打印值,还需要实现 `Debug` trait.通常通过 `#[derive(Debug, PartialEq)]` 一并实现.


```rust
#[derive(Debug, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p1 = Point { x: 1, y: 2 };
    let p2 = Point { x: 1, y: 2 };
    assert_eq!(p1, p2); // 需要 PartialEq + Debug
}
```

## 单元测试(Unit Tests)

Rust 的测试直接写在源码文件中,通过 `#[test]` 属性标记测试函数:

```rust
fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_add() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn test_add_negative() {
        assert_eq!(add(-1, 1), 0);
    }
}
```

- `#[cfg(test)]`:告诉编译器仅在 `cargo test` 时编译此模块(`cfg` = configuration,配置)
- `mod tests`:将测试代码组织在一个模块中(`mod` = module,模块)
- `use super::*`:引入父模块的所有内容
- `#[test]`:标记一个函数为测试用例


> [!info] 测试命令
> 
> ```bash
> cargo test              # 运行所有测试
> cargo test test_add     # 只运行名称包含 test_add 的测试
> cargo test -- --nocapture  # 显示测试中的 println! 输出
> ```
> 


### 测试 panic

使用 `#[should_panic]` 标记预期会 panic 的测试:

```rust
#[test]
#[should_panic(expected = "index out of bounds")]
fn test_panic() {
    let v: Vec<i32> = vec![];
    v[0]; // 预期 panic
}
```


> [!important] 测试的组织方式
> Rust 的测试分为**单元测试**(unit tests,在 `src/` 中用 `#[cfg(test)]` 模块)和**集成测试**(integration tests,在 `tests/` 目录下).单元测试测试内部逻辑,集成测试测试公开 API.


## 从学习项目选择测试边界

测试不应只覆盖一个普通输入.先写出函数的输入域、特殊值和失败表示,再选择边界:

```rust
#[test]
fn fibonacci_covers_base_cases_and_overflow() {
    assert_eq!(fibonacci(0), Some(0));
    assert_eq!(fibonacci(1), Some(1));
    assert_eq!(fibonacci(93), Some(12_200_160_415_121_876_738));
    assert_eq!(fibonacci(94), None); // u64 加法溢出边界
}
```

Fibonacci 的关键边界是两个起始项和 `u64` 可表示范围.`Option<u64>` 让溢出成为可断言的 `None`,而不是依赖 panic.

```rust
#[test]
fn temperature_covers_reference_points() {
    assert_eq!(c_to_f(0.0), 32.0);      // 水的冰点
    assert_eq!(f_to_c(32.0), 0.0);
    assert_eq!(c_to_f(-40.0), -40.0);   // 两个温标的交点
}
```

温度转换选择有物理意义的参考点.涉及非整数浮点运算时,不应盲目使用 `assert_eq!`;可比较误差 `assert!((actual - expected).abs() < 1e-10)`.

```rust
#[test]
fn bubble_sort_orders_generic_values_and_accepts_empty_input() {
    let mut numbers = [5, 1, 4, 2, 8];
    bubble_sort(&mut numbers);
    assert_eq!(numbers, [1, 2, 4, 5, 8]);

    let mut words = ["pear", "apple", "orange"];
    bubble_sort(&mut words);
    assert_eq!(words, ["apple", "orange", "pear"]);

    let mut empty: [i32; 0] = [];
    bubble_sort(&mut empty);
    assert_eq!(empty, []);

    let mut single = [42];
    bubble_sort(&mut single);
    assert_eq!(single, [42]);
}
```

现有测试验证了整数与字符串的排序结果,并覆盖空切片和单元素切片.实际实现的外层是 `for i in 0..len`,内层是 `0..len - 1 - i`:空切片的外层范围为 `0..0`,循环体不执行,所以不会计算会下溢的内层范围;单元素切片的内层范围则为 `0..0`.当前测试尚未覆盖已排序、逆序和重复元素输入.

```rust
#[test]
fn ignores_empty_segments_around_ascii_spaces() {
    let input = "   hello    rust   ";

    assert_eq!(nth_word(input, 0), Some("hello"));
    assert_eq!(nth_word(input, 1), Some("rust"));
    assert_eq!(nth_word(input, 2), None);
}
```

该测试覆盖前导、连续和尾随 ASCII 空格,确认空段被忽略并返回实际单词.同一测试模块中另有断言覆盖空输入和普通输入的越界索引;当前没有测试制表符、换行或其他 Unicode 空白,函数契约也只把 ASCII `b' '` 当作分隔符.

## minigrep:精确验证错误变体

只写 `assert!(result.is_err())` 只能证明“出错了”,不能确认错误原因正确.自定义错误枚举实现 `Debug` 和 `PartialEq` 后,可以直接比较具体变体:

```rust
// src/lib.rs 的 tests 模块,已导入 Config 和 ConfigError
#[test]
fn missing_path() {
    let args = ["minigrep", "nobody"];
    let error = Config::build(args.into_iter().map(String::from))
        .err()
        .expect("缺少路径应返回错误");

    assert_eq!(error, ConfigError::MissingFilePath);
}
```

`.err()` 消耗 Result,把 `Err(e)` 转成 `Some(e)`,把 `Ok(_)` 转成 `None`.之后 `expect` 从 Option 取得错误;如果构建意外成功,测试会 panic.

| 输入 | 应验证的变体 |
| ---- | ------------ |
| `["minigrep"]` | `MissingQuery` |
| `["minigrep", "nobody"]` | `MissingFilePath` |
| `["minigrep", "nobody", ""]` | `EmptyFilePath` |
| `["minigrep", "nobody", "poem.txt", "extra"]` | `TooManyArguments` |


> [!info] 为什么暂不用 unwrap_err
> `Result<T, E>::unwrap_err()` 要求成功类型 `T: Debug`,因为意外得到 Ok 时需要把成功值打印到 panic 信息里.当前 Config 没有实现 Debug,用 `.err().expect(...)` 不需要为这个测试额外改动成功类型.


## 编译期约束测试与运行时断言

可以用一个空辅助函数检查类型是否实现指定 trait:

```rust
fn assert_is_error<E: std::error::Error>() {}

#[test]
fn config_error_implements_error() {
    assert_is_error::<ConfigError>();
}
```

`E: Error` 在**编译期**检查,不需要写运行时断言.`::<ConfigError>` 是 turbofish,显式指定泛型参数;辅助函数没有值参数,编译器不能从实参推断 E.

若移除 `impl std::error::Error for ConfigError {}`,会导致编译失败,测试尚未开始执行;这不是“某条 assert 失败”.

装箱转换与消息保持则可以同时覆盖两个层次:

```rust
#[test]
fn boxed_config_error_preserves_message() {
    let error: Box<dyn std::error::Error> = ConfigError::MissingQuery.into();
    assert_eq!(error.to_string(), "missing query");
}
```

- 编译通过:说明此处要求的类型转换可用.
- 运行时断言通过:说明装箱后仍按 Display 显示预期消息.
- `dyn` 不是因为代码处于测试中而需要;它表示使用 trait 对象,见[泛型与特征](Rust/泛型与特征.md).

## 集成测试:启动真实命令行程序

`tests/cli.rs` 可以用标准库的 Command 启动 Cargo 构建的二进制,检查真实的状态码和输出,不需要第三方测试依赖:

```rust
// tests/cli.rs
use std::path::Path;
use std::process::Command;

#[test]
fn prints_matching_lines() {
    let file_path = Path::new(env!("CARGO_MANIFEST_DIR")).join("poem.txt");
    let output = Command::new(env!("CARGO_BIN_EXE_minigrep"))
        .arg("nobody")
        .arg(file_path)
        .env_remove("IGNORE_CASE")
        .env_remove("SHOW_LINE_NUMBERS")
        .output()
        .expect("应能启动 minigrep");

    assert!(output.status.success());
    assert!(output.stderr.is_empty());
    let stdout = String::from_utf8(output.stdout).expect("输出应为 UTF-8");
    assert_eq!(
        stdout.lines().collect::<Vec<_>>(),
        vec!["I'm nobody! Who are you?", "Are you nobody, too?"],
    );
}
```

- `env!("CARGO_BIN_EXE_minigrep")` 在集成测试编译时获得可执行文件路径;不是运行时读取开关的 `std::env::var`.
- `env!("CARGO_MANIFEST_DIR")` 与 `Path::join` 构造素材路径,避免依赖运行命令时的工作目录.
- `output()` 捕获 stdout/stderr 字节和进程退出状态;`String::from_utf8` 显式验证并转换字节输出.
- `.env` / `.env_remove` 只设置**子进程**的环境,不修改测试进程自身的全局环境.项目开关存在即启用,测试需隔离外部环境,覆盖两个开关的四种组合.
- `status.success()` 检查是否成功;`status.code()` 返回 `Option<i32>`,验证退出码 1 应比较 `Some(1)`.


> [!warning] 不要让提示文本蒙混过关
> 只断言 `stdout.contains("nobody")`,可能会被 `Searching for nobody` 这样的查询提示骗过.比较完整行列表可以同时验证实际内容、数量和顺序;无匹配时应验证 stdout 为空且成功退出.
> 
> 文件读取错误的底层措辞可能随操作系统或语言环境变化.优先检查稳定的应用错误前缀,不要精确匹配整个 OS 错误文本.


搜索的单元测试还应关注:多匹配及顺序、无匹配、空查询、中间空行、大小写、原文缩进保持、原文件行号.例如 `"Rust\nPython\nRust again"` 搜索 Rust 应返回行号 1 和 3,不是 1 和 2.

## 文档注释与文档测试

`///` 为后面的公开接口生成文档,其中的 Rust 示例也可以作为文档测试:

```rust
/// 返回包含查询词的原始行,区分大小写并保持顺序.
///
/// 返回的行借自 contents,不复制每行字符串.
///
/// # Examples
/// ```
/// use minigrep::search;
/// let results = search("Rust", "Rust is fast.\nPython is readable.");
/// assert_eq!(results, vec!["Rust is fast."]);
/// ```
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents.lines().filter(|line| line.contains(query)).collect()
}
```

这里的 `use minigrep::search` 模拟外部调用者使用公开库 API.普通 `//` 注释不会成为这类接口文档.

```bash
cargo test                 # 运行单元测试、集成测试及文档测试
cargo test --doc           # 只运行文档测试
cargo doc --no-deps        # 生成本项目文档,不生成依赖文档
cargo fmt --check          # 检查格式,不等于测试逻辑
```


> [!important] 区分三种验证结果
> 新行为尽量先写测试,确认它因为预期原因失败,再实现功能.编译失败意味着测试无法运行;断言失败意味着测试已执行但结果不符;测试通过也不代表覆盖充分.不要为了消除失败而削弱测试.
