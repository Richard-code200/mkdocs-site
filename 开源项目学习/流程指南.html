阶段一：选对项目

筛选条件

在 GitHub 使用高级搜索筛选候选项目，中等规模最合适，不是越热越好：

快速检查三个指标

  • CONTRIBUTING.md 是否存在 —— 说明项目欢迎新人
  • Issues 中有无 good first issue 标签 —— 有入门任务可做
  • 最近一周有无 commit —— 项目活跃

本地跑通

跑不通就换，跑得通说明文档过关。

具体推荐

一些适合入门的项目（按语言举例）：

  • Go：fzf（CLI 工具，模糊搜索）
  • Python：rich（终端美化，ANSI 转义码）
  • JS：htmx（前端库，增量 HTML）
  • Rust：bat（cat 替代品，代码量适中）

阶段二：先成为用户

熟悉全部功能

把项目的所有 CLI 子命令或 API 方法罗列出来，每个都亲自跑一遍，记录输出是什么。

猜实现并验证

挑 3 个你最感兴趣的功能，写出”我猜它是怎么实现的”。

例如你用 rich 打印彩色表格，先猜它怎么处理 ANSI 转义码，再去源码中验证。

用调试器跟踪调用栈

根据你使用的语言选择调试器：

发起一个请求或命令，打断点后单步跟进去看调用栈。这是理解项目结构的捷径。

阶段三：带着问题读源码

不要从 main() 直接读，按以下三圈递进。

第 1 圈：读懂接口层

找项目的 public API 或 entry point：

语言查找方式
Python__init__.py 里 __all__ 列出的符号
Go包根目录导出的函数（首字母大写）
Rustlib.rs 里的 pub mod + pub fn
JS/TSindex.ts 中的 export 语句

逐个看函数签名和 docstring，不要看实现。

第 2 圈：追踪功能的完整链路

选一个阶段二中猜过的功能，用”漏斗法”逐层追踪：

  • 顶层：用户调用的那个函数
  • 中层：它调了谁？数据在哪些对象间流转？
  • 底层：最终落到什么系统调用或网络请求？

画一张调用关系草稿（纸笔或 Excalidraw），只画你追过的地方。

第 3 圈：读最早期的 commit

看作者第一版代码有多简单，消除”大神写的肯定看不懂”的心理障碍。

实操技巧

  • 用 rg "函数名" --type py（或对应语言）快速跳转定义处
  • 随手在源码旁记下你的理解，用 # 注释 标记（不要提交）
  • 遇到看不懂的，Google 搜 项目名 + 函数/类名 + blog，大概率有人写过分析

阶段四：写最小原型

剥离核心模块

只复制一个核心模块到新目录：

删掉所有外部依赖，只剩这一个模块。

用自己的方式重写

  • 变量名按你的习惯改
  • 删掉边界处理、性能优化，只保留核心逻辑
  • 每改 20 行跑一次测试，看有没有崩

与原版对比

看作者的实现和你有什么不同。这个时候你才能真正看懂那些”多余代码”是干嘛的。

阶段五：参与贡献

不要一上来就”我要实现新功能”，按难度递增逐步参与。

Level 0：修改文档或注释（第 1 次 PR）

  • 找 README 里的拼写错误
  • 补一个入参说明
  • 翻译一段文档

目的：熟悉 fork → branch → PR → review 全流程。

Level 1：补测试（第 2~3 次 PR）

  • 在 CI 面板找 coverage report
  • 挑一个 coverage 低于 80% 的文件
  • 写 2~3 个单元测试

目的：逼你真正理解输入输出契约。

Level 2：修 bug（第 4~5 次 PR）

  • 挑 good first issue 标签的 bug
  • 先在本地复现，打断点定位，写修复，加回归测试
  • Push 前 git rebase -i 把 commit 压成一个

Level 3：实现小型 feature

  • 先开 issue 描述提案，等 maintainer 点头
  • 参考项目已有的类似 feature 代码，模仿其模式
  • PR 描述写清楚：What / Why / How

注意

不要在这个阶段追求”一次提交完美的代码”。你的目标是通过 review 反馈学习项目的编码规范和设计理念，被指出问题反而是收获最大的时刻。

每日节奏建议

时间段做什么目的
前 30 分钟git pull && 浏览新 commit/issue保持对项目的感知
核心 1.5 小时按阶段三/四深读或写代码真正的学习
最后 20 分钟把今天搞懂的写 3~5 句话笔记积累会复利

常见坑及对策

踩坑对策
看了 30 分钟不知所云，想放弃换个更小的文件重来；或者跳到阶段四先写
遇到不认识的语法或模式立刻查，但只查这一个点，别发散；查到后原地写一行注释标记
总觉得”自己写的太烂不敢发 PR”你第一个 PR 99% 是改 typo，真的没有门槛
项目太大，不知道从哪开始反复回到阶段三第 2 圈，“追踪一个功能”是万能入口
PR 提交后被要求大改正常现象，耐心逐条回应 review 意见即可
