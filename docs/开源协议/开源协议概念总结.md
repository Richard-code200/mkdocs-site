# 开源协议概念总结

## 什么是开源协议

开源协议是一种法律文件，规定了软件的使用者可以如何查看、修改和分发代码。没有协议的代码默认受版权法保护，他人**无权**使用、修改或分发。

开源协议的核心逻辑是：作者保留版权，但通过协议**授予**使用者特定权利，同时可能附加一定义务。

## 核心维度说明

理解一个开源协议，通常从以下维度入手：

1. **Copyleft 强度**：是否要求衍生作品也以相同协议开源
2. **商业友好度**：是否允许将代码用于商业产品或闭源分发
3. **专利授权**：是否明确授予专利权（防止贡献者后期发起专利诉讼）
4. **兼容性**：能否与其他协议的代码混合使用

/// info | Copyleft 是什么
Copyleft 是 GPL 系列协议的核心思想——"自由传染"。如果你使用了带 Copyleft 的代码，你的整个项目也必须以相同协议开源。它用版权法来保护自由，而非限制自由。
///

## MIT 协议

**全称**：The MIT License

**一句话总结**：几乎"想干嘛干嘛"，只需保留版权声明。

### 关键条款

- ✅ 允许商用、闭源、修改、分发、私人使用
- ✅ 不提供任何担保（作者不承担代码出问题的责任）
- ⚠️ 分发时必须附带原版权声明和协议文本
- ❌ **不包含专利授权条款**（理论上作者可以后续就代码中的专利提起诉讼）

### 典型使用场景

绝大多数 npm、Rust crate、小型开源库都使用 MIT。它是最简单、最宽容的协议之一。

```text
MIT License

Copyright (c) 2025 张三

Permission is hereby granted, free of charge, to any person obtaining a copy...
```

/// warning | 注意
MIT 不包含专利授权。如果你担心专利诉讼风险，Apache 2.0 是更好的选择。
///

---

## Apache 2.0 协议

**全称**：Apache License 2.0

**一句话总结**：MIT 的加强版，增加了专利授权和商标保护。

### 关键条款

- ✅ 与 MIT 同样允许商用、闭源、修改、分发
- ✅ **明确授予专利权**：贡献者自动授予使用者相关专利许可
- ✅ **专利诉讼终止**：如果使用者对代码发起专利诉讼，协议自动终止
- ⚠️ 修改过的文件必须声明做了改动
- ⚠️ 保留 NOTICE 文件（如有）

### 与 MIT 的核心区别

| 维度        | MIT    | Apache 2.0 |
| ----------- | ------ | ---------- |
| 专利授权    | 无     | 明确授予   |
| 专利防御    | 无     | 诉讼即终止 |
| NOTICE 文件 | 不需要 | 需保留     |
| 修改声明    | 不强制 | 必须标注   |

Apache 2.0 是目前大公司和基金会（如 Kubernetes、TensorFlow）最常用的协议。

---

## GPL 协议

**全称**：GNU General Public License

**一句话总结**："强 Copyleft"——用了我的代码，你的项目也必须开源。

### GPLv2 vs GPLv3

| 维度               | GPLv2     | GPLv3                 |
| ------------------ | --------- | --------------------- |
| 发布日期           | 1991      | 2007                  |
| 专利条款           | 无        | 有（类似 Apache 2.0） |
| 反 Tivo 化         | 无        | 有（禁止硬件锁死）    |
| 与 Apache 2.0 兼容 | ❌ 不兼容 | ✅ 兼容               |

"Tivo 化"是指硬件设备使用了 GPL 代码，但通过数字签名锁死硬件，阻止用户真正运行修改后的版本。GPLv3 明确禁止这种行为。

### 关键条款

- ✅ 允许商用、修改、分发
- ❌ 分发时必须公开源码（包括使用了 GPL 代码的衍生项目）
- ❌ 如果以二进制形式分发，必须同时提供对应源码或书面提供源码获取方式
- ⚠️ 网络服务（SaaS）不触发分发义务——这是 AGPL 要解决的问题

/// important | GPL 的"传染性"
GPL 不强制你把自己的笔记或内部工具开源。只有当你**分发** GPL 软件时，才需要提供源码。如果仅在内部服务器运行、不对外分发，无需开源。
///

### 典型使用场景

Linux 内核（GPLv2）、GCC、Bash、Git 等 GNU 项目。

---

## AGPL 协议

**全称**：GNU Affero General Public License

**一句话总结**：GPL + "网络也得分发"——补上了 SaaS（软件即服务）漏洞。

### 核心补充

GPL 的"传染"只在**分发**时触发。但 SaaS 服务不"分发"软件——用户只通过网络访问，不拿到代码副本。AGPL 规定：如果你修改了 AGPL 代码并部署为网络服务，**远程访问也算分发**，你必须开源你的改动。

```text
GPL:  你修改代码 → 不对外分发 → 无需开源
AGPL: 你修改代码 → 部署为网络服务 → 必须开源
```

### 典型使用场景

MongoDB、Grafana、MinIO 等需要防止大公司"白嫖"的数据库/基础设施项目。

---

## LGPL 协议

**全称**：GNU Lesser General Public License

**一句话总结**：GPL 的"弱化版"——动态链接库可以闭源使用。

### 核心思想

LGPL 允许闭源应用**动态链接** LGPL 库，只需对库本身的修改开源，应用本身可以闭源。

```text
GPL:  你的闭源应用 <link> GPL库    → 应用必须开源 ❌
LGPL: 你的闭源应用 <link> LGPL库   → 应用可以闭源 ✅（但库的修改需开源）
```

### 典型使用场景

Qt（LGPL 版本）、GTK、glibc 等希望被广泛使用的底层库。

---

## BSD 协议

**全称**：Berkeley Software Distribution License

**一句话总结**：和 MIT 几乎一样，但多了"禁止用作者名义宣传"条款。

### BSD 2-Clause vs BSD 3-Clause

| 条款         | BSD 2-Clause | BSD 3-Clause |
| ------------ | ------------ | ------------ |
| 保留版权声明 | ✅           | ✅           |
| 禁止背书条款 | ❌           | ✅           |
| 免责声明     | ✅           | ✅           |

"禁止背书条款"的含义：你不能说"李四认可我的产品"，除非李四真的认可了。这保护了原始作者的声誉。

### 典型使用场景

FreeBSD 系统、Go 语言部分组件、Nginx。

```text
BSD 2-Clause ≈ MIT（功能几乎等价）
BSD 3-Clause ≈ MIT + 禁止背书
```

---

## MPL 2.0 协议

**全称**：Mozilla Public License 2.0

**一句话总结**："文件级 Copyleft"——单个文件的修改需开源，但可以和闭源代码放在一起。

### 核心特点

- ✅ 允许商用、闭源项目中使用（只需开源 MPL 代码文件本身）
- ✅ 与 Apache 2.0、GPLv2、LGPLv2.1 兼容
- ✅ 包含专利授权条款
- ⚠️ 修改过的 MPL 文件必须开源

```text
GPL copyleft 范围：整个项目
MPL copyleft 范围：单个文件
```

### 典型使用场景

Firefox、Thunderbird、Rust 编译器（部分组件）。

---

## Unlicense / CC0

**一句话总结**：放弃一切权利，进入公共领域。

- **Unlicense**：适用于代码，完全放弃版权和相关权利
- **CC0（Creative Commons Zero）**：适用于文档、图片、数据等非代码内容

/// warning | 法律风险
部分国家的法律不允许作者完全放弃版权（如德国的"作者人格权"）。Unlicense 在这些法域的效力存疑。如果不确定，用 MIT 最保险。
///

| MIT          | ✅   | ✅             | ❌       | 无             | React, jQuery          |

| BSD 3-Clause | ✅   | ✅             | ❌       | 无             | Go                     |

## 协议兼容性

不是所有协议的代码都能混在一起用。关键规则：

```text
兼容方向：宽松 → 严格

MIT/Apache 2.0/BSD  →  可以合并到 GPL 项目中
GPL 代码             →  不能合并到 MIT 项目中

Apache 2.0  ←→  GPLv3 兼容
Apache 2.0  ←→  GPLv2 不兼容（专利条款冲突）
```

/// important | 兼容性黄金法则
你的项目最终协议不能比依赖的任何组件协议更"宽松"。GPL 代码会"传染"整个项目变成 GPL，而 MIT 代码可以安静地待在 GPL 项目里。
///

## 选型建议

| 场景                                   | 推荐协议        |
| -------------------------------------- | --------------- |
| 个人小工具、简单库，不在乎别人怎么用   | MIT             |
| 需要专利保护，公司项目，不想担责       | Apache 2.0      |
| 希望代码修改必须回馈社区               | GPLv3           |
| 基础设施/数据库，防止大公司白嫖        | AGPLv3          |
| 开发库，希望被广泛使用（包括商用软件） | LGPL 或 MPL 2.0 |
| 完全不 care，放弃一切权利              | Unlicense / CC0 |

/// info | 实际建议
如果不确定，**MIT 或 Apache 2.0** 是最安全的选择。它们使用最广泛，市场接受度最高。如果将来想"收紧"协议，随时可以双协议授权（商业授权用 MIT，社区版用 GPL）。
///

## GPL 系列与 MPL 深度对比

### 核心差异一览

/// info | 关于"GPL（通用）"
"GPL"泛指 GPL 协议的共性特征，不区分版本。具体到专利授权、反 Tivo 化、兼容性等细节，需看 GPLv2 或 GPLv3 列。
///

| 维度               | GPL（通用） | GPLv2    | GPLv3    | LGPL           | MPL 2.0      |
| ------------------ | ----------- | -------- | -------- | -------------- | ------------ |
| Copyleft 范围      | 整个项目    | 整个项目 | 整个项目 | 仅库本身       | 单个文件     |
| 闭源衍生           | ❌          | ❌       | ❌       | ✅（动态链接） | ✅（新文件） |
| 专利授权           | 视版本而定  | ❌       | ✅       | ❌             | ✅           |
| 反 Tivo 化         | 视版本而定  | ❌       | ✅       | ❌             | ❌           |
| 与 Apache 2.0 兼容 | 视版本而定  | ❌       | ✅       | ❌             | ✅           |
| 分发时必须开源     | ✅          | ✅       | ✅       | ✅（仅库修改） | ✅（仅文件） |

### 三组关键区别

**GPLv2 vs GPLv3**：GPLv3 增加了专利授权（防止专利诉讼）、反 Tivo 化（禁止硬件锁死阻止用户运行修改后的代码）、以及与 Apache 2.0 的兼容性。Linux 内核坚持使用 GPLv2，因为 Linus Torvalds 反对反 Tivo 化条款。

**GPL vs LGPL**：LGPL 允许闭源软件通过**动态链接**使用 LGPL 库而不被"传染"。但如果你修改了 LGPL 库本身，库的修改必须开源。静态链接则仍需开源整个项目。

**GPL vs MPL**：GPL 的 Copyleft 范围是**整个项目**——链接了 GPL 代码就必须全部开源。MPL 的 Copyleft 范围是**单个文件**——修改了 MPL 文件需要开源该文件，但新增的文件可以闭源。

### 代表性软件

#### GPLv2

| 项目       | 简介                                          |
| ---------- | --------------------------------------------- |
| Linux 内核 | 操作系统内核，坚持 GPLv2 拒绝升级到 GPLv3     |
| Git        | 分布式版本控制系统                            |
| BusyBox    | 嵌入式 Linux 的"瑞士军刀"，集成大量 Unix 工具 |

#### GPLv3

| 项目 | 简介                                              |
| ---- | ------------------------------------------------- |
| GCC  | GNU 编译器套件，支持 C/C++/Rust 等多语言          |
| Bash | GNU 命令行 Shell，大多数 Linux 发行版的默认 Shell |
| GDB  | GNU 调试器                                        |

#### LGPL

| 项目  | 简介                                             |
| ----- | ------------------------------------------------ |
| glibc | GNU C 标准库，几乎所有 Linux 程序都依赖它        |
| GTK   | GUI 工具包，GNOME 桌面环境的基础                 |
| Qt    | 跨平台 GUI 框架（LGPL 版本），KDE 桌面环境的基础 |

/// info | 为什么 glibc 用 LGPL 而非 GPL
glibc 是系统级基础库，如果采用 GPL，所有链接它的程序都必须开源，这会严重阻碍 Linux 生态发展。LGPL 让闭源商业软件也能在 Linux 上运行。
///

#### MPL 2.0

| 项目        | 简介                     |
| ----------- | ------------------------ |
| Firefox     | Mozilla 浏览器           |
| Thunderbird | Mozilla 邮件客户端       |
| LibreOffice | 开源办公套件（部分组件） |

### 选型速查

```text
想让修改必须回馈社区？
├── 是 → 整个项目都要开源 → GPLv3
│        只要求库本身开源 → LGPL
│        只要求单个文件开源 → MPL 2.0
└── 需要防止硬件锁死？ → GPLv3
```

/// warning | GPLv2 与 GPLv3 不兼容
GPLv2 和 GPLv3 之间**不兼容**——不能将 GPLv2 only 的代码与 GPLv3 代码合并。但许多项目声明 "GPLv2 or later"，此时可以选择以 GPLv3 使用。Linux 内核是 "GPLv2 only"，无法与 GPLv3 代码混合。
///
